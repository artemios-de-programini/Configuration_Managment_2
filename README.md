# Инструмент визуализации графа зависимостей npm (Вариант №8)

Консольное приложение для анализа и визуализации графа зависимостей
пакетов формата **JavaScript (npm)**. Штатные менеджеры пакетов и
сторонние библиотеки для получения зависимостей не используются: данные
читаются из обычного HTTP-реестра стандартными средствами Python.

---

## Требования

- Python 3.10 или новее;
- сетевой доступ к реестру npm только для обычного режима; тестовый
  режим работает с локальным файлом и сети не требует.

## Запуск

```bash
./run.sh --package express --repo https://registry.npmjs.org \
         --test-mode false --version 4.19.2 --output graph.svg
```

Для Windows предназначен `run.bat` с теми же параметрами.

---

## Этап 1. Минимальный прототип с конфигурацией

**Цель этапа:** создать минимальное CLI-приложение, считывающее
пользовательскую конфигурацию из аргументов командной строки,
проверяющее все входные параметры и выводящее конфигурацию в формате
`ключ: значение`.

### 1. Параметры командной строки

| Флаг CLI      | Ключ в выводе | Обязательный | Описание и правила проверки |
| :---          | :---          | :---:        | :--- |
| `--package`   | `package`     | да | Имя анализируемого пакета. В обычном режиме проверяется по правилам имён npm (строчные буквы, цифры, дефисы, необязательный `@scope/`). В тестовом режиме допускаются только заглавные латинские буквы (`A`–`Z`). |
| `--repo`      | `repo`        | да | URL-адрес реестра или путь к файлу тестового репозитория. В обычном режиме проверяются схема `http://`/`https://` и наличие домена, в тестовом — существование файла. |
| `--test-mode` | `test_mode`   | да | Режим работы с тестовым репозиторием. Принимает только значения `true` или `false`. |
| `--version`   | `version`     | да | Версия пакета в формате `X.Y.Z` (возможен суффикс, например `1.0.0-beta.1`) или слово `latest`. |
| `--output`    | `output`      | да | Имя файла с изображением графа. Должно заканчиваться на `.svg`, не содержать запрещённых символов `<>:"|?*` и не содержать путь к каталогу. |
| `--ascii-tree`| `ascii_tree`  | нет | Режим вывода зависимостей в виде ASCII-дерева, значения `true` или `false` (по умолчанию `false`). |
| `--reverse`   | `reverse`     | нет | Режим вывода обратных зависимостей (появляется на этапе 4), значения `true` или `false` (по умолчанию `false`). |

### 2. Демонстрация работы

Корректный запуск:

```bash
python3 src/main.py --package express --repo https://registry.npmjs.org \
    --test-mode false --version 4.19.2 --output graph.svg
```

```text
package: express
repo: https://registry.npmjs.org
test_mode: false
version: 4.19.2
output: graph.svg
ascii_tree: false
```

Обработка ошибок: все неверные параметры сообщаются за один запуск, а
программа завершается с кодом `2`.

```bash
python3 src/main.py --package "INVALID!" --repo ftp://x --test-mode yes \
    --version v1.0 --output graph.png
```

```text
Ошибка --test-mode: нужно 'true' или 'false', дано 'yes'.
Ошибка --package: неверное имя пакета 'INVALID!'.
Ошибка --repo: неверный URL 'ftp://x'.
Ошибка --version: неверный формат 'v1.0'.
Ошибка --output: имя файла должно заканчиваться на '.svg'.
```

### 3. Архитектура решения (этап 1)

* `src/main.py` — разбор аргументов командной строки, вывод конфигурации,
  коды возврата;
* `src/config.py` — правила проверки каждого параметра, сбор всех ошибок
  в один список и неизменяемый объект конфигурации `ToolConfig`.

## Этап 2. Сбор данных

**Цель этапа:** получить информацию о прямых зависимостях заданной
пользователем версии пакета, используя URL-адрес репозитория, и вывести
их на экран. Менеджеры пакетов и сторонние библиотеки не используются.

### 1. Как получаются данные

Пакет читается из публичного HTTP-реестра npm. Для версии пакета
запрашивается документ вида `{repo}/{package}/{version}`, из которого
берётся объект `dependencies`; для слова `latest` используется адрес
`{repo}/{package}/latest`. Запросы отправляет `urllib.request` из
стандартной библиотеки Python, ответ разбирает модуль `json`.

### 2. Демонстрация работы

```bash
python3 src/main.py --package express --repo https://registry.npmjs.org \
    --test-mode false --version 4.19.2 --output graph.svg
```

```text
package: express
repo: https://registry.npmjs.org
test_mode: false
version: 4.19.2
output: graph.svg
ascii_tree: false
Прямые зависимости express@4.19.2:
  accepts: ~1.3.8
  array-flatten: 1.1.1
  body-parser: 1.20.2
  ...
  vary: ~1.1.2
```

Пакет без зависимостей:

```text
Прямые зависимости left-pad@1.3.0:
  (нет)
```

Ошибки реестра сообщаются отдельно и завершают программу с кодом `3`:

```text
Ошибка репозитория: реестр вернул HTTP 404 для
https://registry.npmjs.org/absent/1.0.0
```

Тестовый режим подключается на следующем этапе; при его выборе на этом
этапе программа сообщает об этом и завершается с кодом `3`.

### 3. Архитектура решения (этап 2)

* `src/models.py` — неизменяемая модель `Package` (имя, версия, прямые
  зависимости);
* `src/registry.py` — клиент реестра: построение URL, HTTP-запрос,
  разбор JSON, повторные попытки при временных ошибках, исключение
  `RegistryError`;
* `src/main.py` — вывод прямых зависимостей в отсортированном виде.

## Этап 3. Основные операции

**Цель этапа:** построить граф зависимостей с учётом транзитивности,
обойти его алгоритмом BFS без рекурсии, корректно обработать циклы и
поддержать режим тестирования на локальном файле.

### 1. Алгоритм обхода

Граф строится очередью `collections.deque`, рекурсия не используется:
пакет попадает в очередь ровно один раз, поэтому даже граф с циклом
`A -> B -> C -> A` обходится за конечное число шагов. Обратное ребро
сохраняется в графе, но пакет повторно не раскрывается. Цикл ищется
обходом в глубину с явным стеком и выводится в отчёте.

Версии зависимостей разрешаются по диапазонам npm: `^`, `~`, `>=`,
`<=`, `>`, `<`, `=`, частичные версии (`1.2`, `1.x`), `*` и альтернативы
`||`. Для каждого пакета скачивается один документ со всеми версиями,
из него выбирается наибольшая подходящая версия.

### 2. Формат тестового репозитория

Файл состоит из строк `имя: зависимости`, имена — только заглавные
латинские буквы, строки с `#` являются комментариями:

```text
# Базовый граф: общая зависимость D у пакетов B и C
A: B C
B: D
C: D
D:
```

### 3. Демонстрация работы

Тестовый репозиторий без циклов:

```bash
python3 src/main.py --package A --repo examples/repo_basic.txt \
    --test-mode true --version 1.0.0 --output graph.svg
```

```text
Граф зависимостей A:
  всего пакетов: 4
  всего связей: 4
  циклов нет
Пакеты в порядке обхода BFS:
  A (2)
  B (1)
  C (1)
  D (0)
```

Тестовый репозиторий с циклом:

```text
Граф зависимостей A:
  всего пакетов: 3
  всего связей: 3
  цикл: A -> B -> C -> A
Пакеты в порядке обхода BFS:
  A (1)
  B (1)
  C (1)
```

Реальный пакет из реестра:

```bash
python3 src/main.py --package debug --repo https://registry.npmjs.org \
    --test-mode false --version 4.3.4 --output graph.svg
```

```text
Граф зависимостей debug@4.3.4:
  всего пакетов: 2
  всего связей: 1
  циклов нет
Пакеты в порядке обхода BFS:
  debug@4.3.4 (1)
  ms@2.1.2 (0)
```

Готовые демонстрации лежат в `scripts/demo_basic.sh` и
`scripts/demo_cycle.sh`.

### 4. Архитектура решения (этап 3)

* `src/semver.py` — разбор версий, сравнение и проверка диапазонов;
* `src/testrep.py` — чтение и проверка тестового репозитория;
* `src/graph.py` — очередь BFS, поиск цикла, уровни графа;
* `src/registry.py` — кэш документов пакетов и выбор версии по диапазону;
* `src/models.py` — общий интерфейс источника зависимостей.

## Этап 4. Дополнительные операции

**Цель этапа:** вывести на экран обратные зависимости — пакеты, которые
зависят от заданного пользователем пакета.

### 1. Как это работает

Прямой граф строится тем же обходом BFS, затем все рёбра меняют
направление, и обход повторяется от целевого пакета: очередь BFS
поднимается по графу «вверх», поэтому в отчёт попадают пакеты первого
уровня, затем второго и так далее. Циклы не приводят к зацикливанию —
пакет попадает в результат один раз.

Обратные зависимости вычисляются только в тестовом режиме: там известен
весь граф, поэтому ответ полный. Публичный реестр npm не предоставляет
обратного индекса «кто зависит от пакета», и получить полный список
средствами HTTP-API нельзя, о чём программа сообщает явно.

### 2. Демонстрация работы

Граф `examples/repo_basic.txt`:

```text
A: B C
B: D
C: D
```

```bash
python3 src/main.py --package D --repo examples/repo_basic.txt \
    --test-mode true --version 1.0.0 --output graph.svg --reverse true
```

```text
Граф тестового репозитория: пакетов 4, связей 4
Обратные зависимости для D:
  всего пакетов: 3
  B
  C
  A
```

Пакет без обратных зависимостей:

```text
Обратные зависимости для A:
  (нет)
```

Попытка использовать режим без тестового репозитория:

```text
Ошибка: обратные зависимости вычисляются только в тестовом режиме,
где известен весь граф зависимостей.
```

Готовая демонстрация — `scripts/demo_reverse.sh`.

### 3. Архитектура решения (этап 4)

* `src/graph.py` — `build_full_graph` (весь тестовый репозиторий),
  `reverse_edges` (обратные рёбра) и `reachable` (BFS по обратному
  графу);
* `src/main.py` — режим `--reverse` и отдельный отчёт.

## Этап 5. Визуализация

**Цель этапа:** получить графическое представление графа зависимостей и
сравнить его с выводом штатных инструментов.

### 1. Текстовое представление Graphviz

Для любого графа формируется документ DOT, совместимый с утилитой
`dot`; он печатается на экран и сохраняется рядом с изображением в файл
с расширением `.dot`:

```text
digraph dependencies {
    rankdir="LR";
    node [shape=box, style="rounded", fontname="Helvetica"];
    "chalk@4.1.2" [style="rounded,filled", fillcolor="#dbeafe"];
    "ansi-styles@4.3.0";
    "supports-color@7.2.0";
    "chalk@4.1.2" -> "ansi-styles@4.3.0";
    "chalk@4.1.2" -> "supports-color@7.2.0";
}
```

### 2. Изображение SVG

Картинка собирается самим приложением средствами стандартной библиотеки
(`xml.etree.ElementTree`), поэтому установка Graphviz не требуется.
Пакеты раскладываются по уровням обхода BFS: корень слева, его
зависимости — следующими колонками. Каждый узел — скруглённый
прямоугольник с подписью `имя@версия`, корень выделен цветом, каждое
ребро — стрелка. Полное имя пакета хранится в элементе `<title>`, поэтому
при наведении курсора видно подпись целиком.

### 3. ASCII-дерево

При `--ascii-tree true` тот же граф печатается в терминале; повторные
узлы и циклы помечаются, чтобы дерево не разрасталось бесконечно:

```text
A
├── B
│   └── D
└── C
    └── D (повтор)
```

### 4. Примеры для трёх пакетов

```bash
./scripts/demo_real_debug.sh
./scripts/demo_real_chalk.sh
./scripts/demo_real_express.sh
```

| Пакет            | Пакетов | Связей | Файл SVG        |
|------------------|---------|--------|-----------------|
| `debug@4.3.4`    | 2       | 1      | `results/debug.svg`   |
| `chalk@4.1.2`    | 6       | 5      | `results/chalk.svg`   |
| `express@4.19.2` | 71      | 128    | `results/express.svg` |

Дерево `chalk@4.1.2`:

```text
chalk@4.1.2
├── ansi-styles@4.3.0
│   └── color-convert@2.0.1
│       └── color-name@1.1.4
└── supports-color@7.2.0
    └── has-flag@4.0.0
```

### 5. Сравнение со штатными средствами

Прямые зависимости, которые показывает сам npm, совпадают с данными
инструмента:

```text
$ npm view chalk@4.1.2 dependencies
{ 'ansi-styles': '^4.1.0', 'supports-color': '^7.1.0' }
```

Полное дерево npm строит иначе. Для `express@4.19.2` файл
`package-lock.json` содержит 68 записей (67 уникальных имён), а
инструмент строит 70 имён и 71 узел. Причины расхождений:

| Причина | npm | Инструмент |
|---------|-----|------------|
| Выбор версии | дедупликация и повторное использование уже выбранной версии | наибольшая версия, подходящая под каждый диапазон независимо |
| Учёт зависимостей | dev, optional и peer зависимости при соответствующих флагах | только поле `dependencies` пакета |
| Формат графа | дерево установленных каталогов `node_modules` | граф «пакет@версия» с общими узлами |
| Источник | lock-файл проекта, если он есть | всегда свежие метаданные реестра |

Единственное расхождение по версиям в этом примере — `get-intrinsic`:
npm выбрал `1.3.0`, инструмент — `1.3.1` (наибольшую подходящую). В
версии `1.3.1` появились три новые зависимости (`async-function`,
`async-generator-function`, `generator-function`), поэтому граф
инструмента на три пакета больше.

Graphviz-совместимый DOT можно отдать утилите `dot -Tsvg`: набор узлов и
рёбер будет тем же, но расположение узлов окажется другим, потому что
`dot` использует собственный алгоритм ранжирования, а не уровни BFS.
Собственный рендер выбран, чтобы инструмент работал без установленного
Graphviz.

### 6. Архитектура решения (этап 5)

* `src/render.py` — DOT, раскладка по уровням, SVG через
  `xml.etree.ElementTree`, ASCII-дерево с явным стеком;
* `src/main.py` — запись `.dot` и `.svg`, вывод дерева по флагу.

## Структура репозитория

```text
src/
  main.py       точка входа, разбор аргументов и вывод результатов
  config.py     проверка параметров и вывод конфигурации
  models.py     модель пакета и общий класс ошибок источника
  registry.py   клиент HTTP-реестра npm и разрешение версий
  semver.py     семантические версии и диапазоны
  testrep.py    чтение файла тестового репозитория
  graph.py      обход BFS, поиск циклов
  render.py     DOT, SVG и ASCII-дерево
tests/          модульные и сквозные тесты (unittest)
examples/       тестовые репозитории для демонстрации
scripts/        скрипты демонстрационных запусков
results/        создаётся при запуске, содержит .dot и .svg
run.sh          скрипт запуска для Linux и macOS
run.bat         скрипт запуска для Windows
```

python3 -m unittest discover -s tests -v
